# TCP三次握手与四次挥手详解

## 概念介绍

TCP（Transmission Control Protocol，传输控制协议）是一种面向连接的、可靠的、基于字节流的传输层通信协议。TCP连接的建立与终止需要通过特定的握手与挥手过程来确保通信的可靠性。

三次握手（Three-way Handshake）是TCP建立连接的过程，而四次挥手（Four-way Wavehand）是TCP终止连接的过程。理解这些过程对于掌握网络通信原理和排查网络问题至关重要。


TCP的三次握手和四次挥手是确保数据可靠传输的重要机制，具体过程如下：

目的是让双方确认彼此的发送和接收能力正常，确定初始序列号。

1.	客户端→服务器（SYN=1，seq=x）：客户端发送连接请求，标志位SYN设为1，随机生成初始序列号x，进入SYN_SENT状态。

2.	服务器→客户端（SYN=1，ACK=1，seq=y，ack=x+1）：服务器收到请求后，确认客户端的序列号（ack=x+1），同时自己也发送SYN请求（SYN=1），生成初始序列号y，进入SYN_RCVD状态。

3.	客户端→服务器（ACK=1，seq=x+1，ack=y+1）：客户端确认服务器的序列号（ack=y+1），标志位ACK设为1，双方进入ESTABLISHED状态，连接建立完成。
二、四次挥手（断开连接）

目的是确保双方都已完成数据传输，安全关闭连接（因TCP是全双工通信，需双向关闭）。

1. 客户端→服务器（FIN=1，seq=u）：客户端数据发送完毕，发送断开请求（FIN=1），进入FIN_WAIT_1状态。
2. 服务器→客户端（ACK=1，seq=v，ack=u+1）：服务器收到请求后，先确认客户端的断开（ack=u+1），此时服务器可能仍有数据要发，进入CLOSE_WAIT状态；客户端收到确认后，进入FIN_WAIT_2状态，等待服务器数据发完。
3. 服务器→客户端（FIN=1，ACK=1，seq=w，ack=u+1）：服务器数据发送完毕，也发送断开请求（FIN=1），进入LAST_ACK状态。
4. 客户端→服务器（ACK=1，seq=u+1，ack=w+1）：客户端确认服务器的断开（ack=w+1），进入TIME_WAIT状态（等待一段时间，确保服务器收到确认），之后关闭连接；服务器收到确认后，直接关闭连接。

## 三次握手过程详解

TCP三次握手的目的是建立可靠的连接，同步连接双方的序列号和确认号，并交换TCP窗口大小等参数。

### 三次握手步骤

1. **第一次握手（SYN=1，seq=x）**

   - 客户端发送一个TCP报文，标志位SYN（同步序列编号）设为1
   - 生成一个随机的初始序列号seq=x
   - 客户端进入SYN_SENT状态，等待服务器确认
2. **第二次握手（SYN=1，ACK=1，seq=y，ack=x+1）**

   - 服务器收到客户端的SYN报文后，需要确认客户端的SYN
   - 服务器也发送一个SYN信号（SYN=1），并生成自己的初始序列号seq=y
   - 服务器将确认序号ack设置为客户端的seq+1（x+1）
   - 服务器进入SYN_RCVD状态
3. **第三次握手（ACK=1，seq=x+1，ack=y+1）**

   - 客户端收到服务器的SYN+ACK报文后，向服务器发送确认报文ACK
   - 确认号ack设置为服务器的seq+1（y+1）
   - 客户端自己的序列号seq设置为x+1
   - 客户端和服务器都进入ESTABLISHED状态，连接建立完成

### 三次握手状态变化

```
客户端状态: CLOSED → SYN_SENT → ESTABLISHED
服务器状态: CLOSED → LISTEN → SYN_RCVD → ESTABLISHED
```
### 三次握手示意图

```
客户端                  服务器
  |                      |
  |  SYN=1, seq=x        |
  |--------------------->|
  |                      |
  |  SYN=1, ACK=1,       |
  |  seq=y, ack=x+1      |
  |<---------------------|
  |                      |
  |  ACK=1, seq=x+1,     |
  |  ack=y+1             |
  |--------------------->|
  |                      |
  |     连接已建立       |
  |                      |
```
## 四次挥手过程详解

TCP四次挥手用于终止连接，确保双方都能正确关闭连接并处理剩余数据。

### 四次挥手步骤

1. **第一次挥手（FIN=1，seq=u）**

   - 主动关闭方发送FIN报文，标志位FIN设为1
   - 序列号seq=u（当前发送方的序列号）
   - 主动关闭方进入FIN_WAIT_1状态
2. **第二次挥手（ACK=1，ack=u+1）**

   - 被动关闭方收到FIN报文后，发送ACK确认
   - 确认号ack=u+1
   - 被动关闭方进入CLOSE_WAIT状态
   - 主动关闭方收到确认后进入FIN_WAIT_2状态
3. **第三次挥手（FIN=1，seq=v）**

   - 被动关闭方完成数据发送后，也发送FIN报文
   - 序列号seq=v
   - 被动关闭方进入LAST_ACK状态
4. **第四次挥手（ACK=1，ack=v+1）**

   - 主动关闭方收到FIN报文后，发送ACK确认
   - 确认号ack=v+1
   - 主动关闭方进入TIME_WAIT状态
   - 被动关闭方收到确认后进入CLOSED状态
   - 主动关闭方等待2MSL后进入CLOSED状态

### 四次挥手状态变化

```
主动方状态: ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
被动方状态: ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED
```
### 四次挥手示意图

```
主动关闭方              被动关闭方
  |                      |
  |  FIN=1, seq=u        |
  |--------------------->|
  |                      |
  |  ACK=1, ack=u+1      |
  |<---------------------|
  |                      |
  |                      | (可能还在传输数据)
  |                      |
  |  FIN=1, seq=v        |
  |<---------------------|
  |                      |
  |  ACK=1, ack=v+1      |
  |--------------------->|
  |                      |
  |   (等待2MSL后关闭)   |
  |                      |
```
## 核心技术要点

### 1. 序列号与确认号

- **序列号(seq)**：表示发送数据的字节流起始位置，随机初始化后自增
- **确认号(ack)**：表示期望收到对方下一个字节的序号，即已成功接收的字节序号+1
- 序列号的随机初始化是为了防止历史连接的报文被错误接收

### 2. 关键标志位


| 标志位 | 名称 | 作用描述                               |
| ------ | ---- | -------------------------------------- |
| SYN    | 同步 | 用于建立连接，同步序列号               |
| ACK    | 确认 | 表示确认号字段有效                     |
| FIN    | 结束 | 用于释放连接，表示发送方已完成数据发送 |
| RST    | 重置 | 用于重置连接，通常在发生错误时使用     |
| PSH    | 推送 | 强制将数据立即发送给应用层，不缓存     |
| URG    | 紧急 | 指示紧急数据，应优先处理               |

### 3. TIME_WAIT状态

- **持续时间**：2MSL（Maximum Segment Lifetime，报文最大生存时间），通常为2分钟
- **作用**：
  1. 确保最后一个ACK报文能被对方收到
  2. 防止已失效的连接报文出现在新连接中
- **危害**：大量TIME_WAIT连接会占用系统端口资源
- **优化**：可通过调整`net.ipv4.tcp_tw_reuse`和`net.ipv4.tcp_tw_recycle`参数优化

### 4. 半关闭状态

- TCP连接是全双工的，支持半关闭状态
- 当一方发送FIN后，只能接收数据，不能发送数据
- 应用程序需要正确处理半关闭状态以避免连接挂起

## 常见面试问题

### 1. 为什么需要三次握手而不是两次？

三次握手是为了防止失效的连接请求报文段被服务端接收，从而产生错误。

- 两次握手情况下：客户端发送的SYN报文可能因网络延迟而滞留，客户端超时重传后建立连接并通信结束
- 若滞留的SYN报文此时到达服务端，服务端会认为是新的连接请求，发送SYN+ACK并建立连接
- 客户端不会理会服务端的SYN+ACK，导致服务端一直等待客户端确认，浪费资源
- 三次握手通过第三次确认，确保双方都准备好建立连接

### 2. 为什么四次挥手需要等待2MSL？

2MSL等待是TCP可靠性的重要保障：

1. **确保最后一个ACK能被对方接收**：若最后一个ACK丢失，被动关闭方会重发FIN，此时主动关闭方仍在TIME_WAIT状态，可重新发送ACK
2. **防止失效报文干扰新连接**：等待足够长时间让网络中所有该连接的报文都消失，避免干扰使用相同端口的新连接

### 3. 为什么四次挥手需要四次而不是三次？

TCP连接是全双工的，双方需要独立关闭各自的发送通道：

- 当主动关闭方发送FIN时，仅表示它不再发送数据，但仍可接收数据
- 被动关闭方可能还有数据要发送，不能立即发送FIN
- 需要先发送ACK确认收到FIN，等所有数据发送完成后再发送FIN
- 因此需要额外的一个报文段，形成四次挥手

### 4. TCP如何保证可靠性？

TCP通过多种机制保证数据传输的可靠性：

1. **确认机制**：对收到的数据进行确认（ACK）
2. **超时重传**：发送数据后设置定时器，超时未确认则重传
3. **序列号**：确保数据按序到达，去重和重组
4. **流量控制**：通过滑动窗口机制控制发送速率
5. **拥塞控制**：慢启动、拥塞避免、快速重传、快速恢复
6. **校验和**：检测数据在传输过程中的错误

### 5. TCP与UDP的主要区别


| 特性     | TCP                                    | UDP                              |
| -------- | -------------------------------------- | -------------------------------- |
| 连接类型 | 面向连接                               | 无连接                           |
| 可靠性   | 可靠传输                               | 不可靠传输                       |
| 传输效率 | 较低                                   | 较高                             |
| 适用场景 | 数据完整性要求高（文件传输、网页浏览） | 实时性要求高（视频流、语音通话） |
| 头部大小 | 20-60字节                              | 8字节                            |
| 拥塞控制 | 有                                     | 无                               |
| 流量控制 | 有                                     | 无                               |

## 代码演示

### Node.js实现TCP服务器与客户端

```javascript
// TCP服务器
const net = require('net');

const server = net.createServer((socket) => {
  console.log('客户端已连接');

  socket.on('data', (data) => {
    console.log(`收到客户端数据: ${data.toString()}`);
    socket.write('服务器已收到数据: ' + data.toString());
  });

  socket.on('end', () => {
    console.log('客户端已断开连接');
  });
});

server.listen(8080, () => {
  console.log('TCP服务器已启动，监听端口8080');
});

// TCP客户端
const client = net.connect({ port: 8080 }, () => {
  console.log('已连接到服务器');
  client.write('Hello TCP服务器!');
});

client.on('data', (data) => {
  console.log(`收到服务器数据: ${data.toString()}`);
  client.end(); // 主动关闭连接
});

client.on('end', () => {
  console.log('已从服务器断开连接');
});
```

## 实际应用与优化

### 1. 连接复用

- 使用HTTP/1.1的Keep-Alive或HTTP/2的多路复用减少TCP连接建立开销
- 实现长连接机制，避免频繁的三次握手和四次挥手

### 2. 性能优化

- **SYN Cookie**：防御SYN Flood攻击，在半连接队列满时使用
- **TCP Fast Open**：减少握手延迟，允许在SYN报文中携带数据
- **端口重用**：通过`SO_REUSEADDR`选项允许快速重用处于TIME_WAIT状态的端口

### 3. 常见问题排查

- **连接建立失败**：检查防火墙规则、端口占用情况、网络可达性
- **连接重置(RST)**：通常由端口未监听、连接超时、数据格式错误等引起
- **大量TIME_WAIT连接**：可通过调整内核参数`net.ipv4.tcp_max_tw_buckets`限制

## 扩展知识

### 1. TCP连接建立的安全风险

- **SYN Flood攻击**：攻击者发送大量SYN报文但不完成三次握手，耗尽服务器资源
- **防御措施**：SYN Cookie、半连接队列限制、源IP过滤

### 2. 现代TCP协议扩展

- **TCP BBR**：Google开发的拥塞控制算法，基于带宽和延迟的估计
- **TCP Fast Open**：允许在SYN报文中携带应用数据，减少握手延迟
- **Multipath TCP**：允许通过多个路径传输数据，提高可靠性和吞吐量
